## 2. 基础业务对象及所有权

| 对象 | 负责维护什么 | 不应重复维护什么 |
| --- | --- | --- |
| 模型资料 | 名称、规范身份、类型、模态、能力和介绍 | 不为每个供应商复制一份主档 |
| 供应商与供应模型 | 采购主体及其提供同款模型的明确关系 | 不承担对外服务售价和客户授权 |
| 渠道与渠道模型映射 | 地址、协议、上游鉴权；模型资料与上游模型标识的关系；模型、渠道维度的采购项 | 不把相同地址或相似名称当成同一身份 |
| 模型服务 | 对外调用身份、服务模式、售价和模型服务级开放范围 | 不再复制一套可编辑的模型身份或供给配置 |
| 服务模型映射 | 当前对外服务采用哪条已登记供给、平台接口及转发规则 | 不在映射表单中再次输入另一份上游地址、密钥和采购价 |
| 路由 | 在当前服务已启用映射中选出实际承接请求的供给 | 不负责创建供应商、修改采购价或改变客户售价 |
| 订购、Key 和调用 | 客户使用资格、Key 授权、实际请求与计量事实 | 不由运营勾选“可见”替代这些资格 |

渠道可以共用连接配置，但服务采用的是明确的“模型资料＋供应商＋渠道＋上游模型标识”关系。状态和操作必须注明作用于一个模型供给、整个共享渠道，还是整个供应商。

### 中英文字段口径

| 中文展示 | 英文字段或概念 | 约束 |
| --- | --- | --- |

## 4. 模型映射如何设计

### 4.1 必须区分两层映射

供应侧的渠道模型映射：模型资料 → 供应商 → 渠道内上游模型标识。接入渠道时保存，属于供应事实。

服务侧的模型映射：对外调用标识 → 已登记的渠道模型映射 → 平台与上游的接口对应。配置在模型服务中，属于允许对客使用的供给关系。

不能用改写规范模型标识代替映射，也不能把“关联渠道”直接等同于当前路由。协议兼容规则只能说明允许映射，不能代替一条可查看、可维护的业务记录。

```mermaid
flowchart LR
    C[客户使用对外调用标识] --> S[模型服务]
    S --> R[当前生效路由]
    R --> M[已启用的服务模型映射]
    M --> U[供应商的渠道模型映射]
    U --> A[上游地址及上游模型标识]
    D[统一模型资料身份] -.明确关联.-> S
    D -.明确关联.-> U
```

### 4.2 映射配置与表格

位置：“路由及映射”页签内，先“模型映射”，后“路由配置”。不增加独立全局网关页面，不重复维护上下游地址。

映射表格至少展示：映射名称、对外调用标识、供应商、渠道、上游模型标识、平台接口 → 上游协议、映射状态、路由引用、操作。同一供应商下多个映射需要可区分；名称只是标签，不能代替稳定关联。

| 配置项 | 填写方式 | 检查或预览 |
| --- | --- | --- |
| 当前模型及对外调用标识 | 从当前服务读取 | 不修改其他服务身份 |
| 供应商 | 选择同一模型资料下已有供应商；分供应商模式固定当前供应商 | 不允许混入其他供应商服务范围 |
| 渠道模型供给 | 选择有效、已验证并启用的登记关系 | 保留上游标识，不按显示名称猜测对应模型 |
| 上游标识、协议、地址 | 从所选关系读取，只读并提供维护跳转 | 防止新建第二套容易失同步的连接配置 |
| 平台接口 | 从当前服务支持的接口中选择 | 本期文本主线使用 OpenAI Chat |
| 映射规则 | 同协议转发与模型标识替换 | 预览客户侧 `model` 与上游侧 `model`、接口路径及必要的固定字段 |
| 状态 | 保存、验证、显式启用或停用 | 供给及接口变化后标出受影响验证，不能复用不匹配回执 |

预览不执行调用，不显示鉴权原文。平台对客的响应身份、错误及调用指南采用同一个对外服务身份；后台保留实际上游身份，不把内部地址、密钥或采购信息透给客户。

基础一期不提供任意脚本、任意 JSON 字段转换或跨协议自定义编辑器。不支持的协议组合明确显示原因；允许选用已支持适配，不把 URL 改写当成协议转换。

### 4.3 操作与边界

| 操作 | 前提 | 生效与影响 |
| --- | --- | --- |
| 新增映射 | 服务身份明确，供给关系有效 | 保存关系，不自动启用或加入路由 |
| 编辑映射 | 有维护权限，当前记录未被他人修改 | 修改先验证后应用，旧有效映射在应用前继续服务 |
| 预览映射 | 配置足够构造脱敏请求 | 只读，不发送请求、不写状态 |
| 验证映射 | 当前供给及平台接口明确 | 在管理验证上下文显式指定本条映射，核对平台身份到上游请求的对应；不依赖正式路由、不开放客户权限，回执绑定当前配置 |
| 启用映射 | 必要验证有效、供给可用 | 可被当前服务路由选择，不自动分配流量 |
| 停用映射 | 已移出生效路由，或相应路由已停用 | 禁止后续路由使用，保留关系及历史 |
| 解除映射 | 无生效路由、在途请求和未完成任务依赖 | 解除当前服务关系，保留供应资源及历史 |

未保存输入仅在当前表单保留。已有的待验证连接配置是明确保存的变更对象，不新增通用“保存草稿/恢复草稿”功能。

诊断结果与启用状态分开。若当前配置已有匹配、有效且覆盖必要项目的验证证据，应复用，不要求运营为不同按钮重复付费验证同一内容。只有单 Key 健康结果，不能替代整个供给及平台映射验证。

验证分工：供应检测确认地址、鉴权及上游模型；映射验证确认所选平台身份与该供给的请求对应，可以在正式路由不存在时执行；上架前的平台试调用使用已生效路由核对整项服务。后者不是前两者才能开始的循环依赖，三个步骤也不强制重复执行同一请求。

## 5. 路由配置如何设计

### 单渠道基础方案

新服务提供“固定渠道”方案，明确选择一条已启用映射。选择是编辑输入，只有确认“保存并生效”才投入；不能因为只找到一个候选就自动分配流量。

候选以稳定模型资料关系和当前服务允许的供应范围确定。映射名、上游标识文字相同，都不能代替同款模型及接口能力检查。其他模型供给不作为普通候选；跨模型替代不纳入本期。

### 日常调整

1. 固定路由替换：新供给 → 新映射 → 验证 → 一次确认把旧映射换成新映射。旧配置在切换成功前生效。
2. 映射移除：有其他有效映射时先改路由；没有替代时先停止对应服务，再停用路由，最后解除映射。
3. 停用路由：仅当对应服务已停止接受新调用时允许执行。保留原配置和历史，不要求提交违反固定策略规则的空路由。
4. 路由恢复：重新核对供给、映射、价格和必要验证，再明确启用。恢复路由不会自动上架服务。

已有加权分流、延迟策略、故障转移字段及历史保持，不因新建默认固定而重写。新手主线不要求填写权重，不恢复版本管理 UI，不新增自动故障转移。

新请求使用新配置，已开始请求沿用原选择和价格快照。替换失败保留原配置；没有可用映射时不能显示为正常可调用。

## 6. 日常维护的业务操作覆盖

| 编号 | 维护任务 | 必须能完成的业务操作 | 影响和退出规则 |
| --- | --- | --- | --- |
| D01 | 修改展示资料 | 打开原主档或卡片、修改、查看共享影响、发布 | 名称变化不改调用身份，不清空无关验证 |
| D02 | 修改能力 | 查看供给及服务引用、修改能力、确认必要下架、重新验证及上架 | 只影响相关依赖，不能用未知能力补造支持 |
| D03 | 新增备用供给 | 接入并启用供给；按需要建立未投入路由的映射 | 备用完成不等于承接流量，不重复建服务 |
| D04 | 替换在用渠道 | 新增映射、验证、改选固定路由、确认切换 | 保留客户身份和售价，旧渠道切换前继续服务 |
| D05 | 修改/停用映射 | 编辑、预览、验证后应用；停用或解除 | 不直接覆盖仍被引用的供应事实，不影响无关服务 |
| D06 | 修改上游标识 | 无引用时直接维护；有引用时准备新供给再切换 | 不让一处编辑悄悄改变所有共享服务 |
| D07 | 修改地址或密钥 | 查看共享影响、保存待验证配置、验证并应用、取消未应用变更 | 原有效配置在确认前服务；独立 Key 留空保留 |
| D08 | 密钥紧急撤销 | 明确选择资产、查看影响、确认撤销 | 立即停止该密钥；无替代时明确停服，不能伪装无损 |
| D09 | 采购调价 | 修改采购项、价格、条件及单位，确认生效 | 不改客户售价，不重算历史 |
| D10 | 客户调价 | 编辑并预览当前服务售价，确认发布 | 含已有订购的新请求使用新价；在途及历史保留 |
| D11 | 修改开放范围 | 编辑、显示新增/移除客户、确认发布 | 模型服务级一份名单，两种模式共用；不自动订购或授权 Key |
| D12 | 控制展示 | 模型可见性、供应商展示状态切换 | 隐藏不等于停服；显示不等于上架或授权 |
| D13 | 停服与恢复 | 整项下架并停用；分供应商单独停服/恢复 | 暂停调用时不接受新的对应订购；已有有效订单保留 |
| D14 | 停用供应资源 | 停用当前模型供给、冻结共享渠道、停用供应商 | 区分三个作用范围；正常维护先迁移引用，紧急操作明确后果 |
| D15 | 解除和删除 | 查看引用、停用路由、解除映射、解绑供应商、删除渠道及登记 | 最后一条映射有退出路径；所有历史及其他引用保留 |
| D16 | 服务退出及恢复 | 归档无有效依赖的服务、查历史、显式恢复并重验 | 记录不物理擦除，对外调用标识不分配给无关模型 |
| D17 | 模式和调用身份调整 | 明确变更前后标识、价格和路由，确认客户影响后重配 | 不自动把旧订购或旧标识等同为新模式服务 |
| D18 | 故障处理 | 从 Request ID 定位服务、映射及实际渠道，再进入对应维护任务 | 不把报表中显示一条错误当作完成处置 |

| 模型用户不可见 | 模型广场隐藏 | 原有资格规则继续检查；已有调用不因隐藏停止 | 保留 |
| 分供应商的下架供应商 | 提供方选择中隐藏 | 原 API 权限保持；不能视为已经停服 | 保留 |
| 分供应商的停服供应商 | 展示状态单独保留；暂停时不作为可订购供给 | 当前供应商服务不接受新订购及新调用，其他供应商不变 | 保留 |
| 模型下架并停用 | 不再作为可订购服务提供 | 整项服务停止新订购及新调用 | 保留，已有请求完成 |
| 停用供给/冻结渠道 | 内部仍可查看及维护 | 对应供给不能承接新上游请求 | 保留，处理全部引用 |
| 停用路由 | 内部保留配置 | 前提为相应服务已停服 | 保留原路由，允许解除引用 |
| 解除、解绑或归档 | 按关系解除或退出有效列表 | 不授予其他调用资格 | 历史及其他对象保持 |

不新增独立“停售”状态。整项服务先沿用“下架并停用”，分供应商保留展示和停服两个维度。正常启用供给、解冻、恢复路由不会自动恢复对客上架。

## 7. 数据、变更与客户影响

1. 保留全部现有手工资料、供应登记、渠道、密钥元数据、映射、路由、价格和客户配置；不重新安装初始数据，不重置目录，不按名称合并资源。
2. 当前关系能从稳定引用确定时，在新页面展示原关系；缺失或歧义的引用明确待补齐。不能自动生成一条启用映射、自动选一个渠道或自动向全部客户开放来补齐状态。
3. 文档中的 GLM-5.5 只用于说明。后续页面不自动写入这一模型、示例地址、密钥、报价或服务。
4. 对外调用标识和上游标识分别保存。调整供给不改客户标识；资料改名不改稳定记录身份。
5. 编辑、取消、导航和预览不保存业务数据。检测不自动启用；启用映射不自动加入路由；恢复供应商不自动上架模型。
6. 需要调用的变更，先验证后明确应用。只改变成本、名称或展示的任务，不无故停止原服务或重置连接证据。
7. 每次确认只提交当前任务。平台验证选用客户不顺带发布开放范围；发布路由不夹带价格和资料修改。
8. 并发修改或保存失败时保留当前输入及原有效配置；未知提交结果按同一次操作查询，不重复创建对象。
9. 采购和销售分别核算，币种和单位不省略；免费为显式 0，缺失是缺失。历史保留调用时快照。
10. 原始供应密钥不进入日志、页面回显、文档、审计或持久化数据；本原型保留既有脱敏实现边界，不因补页面自行引入真实上游或凭证库。

## 8. 异常、停止与恢复的完整性核对

| 情况 | 设计要求 |
| --- | --- |
| 资料已存在 | 复用主档，不能因供应商不同重复创建 |
| 服务已存在 | 去维护、新增映射或准备供给，不再建第二个活动服务 |
| 资料或供应信息不完整 | 说明已完成到哪一步；允许继续维护已保存对象，不能假成功或强填未知值 |
| 映射不匹配 | 显示模型身份、协议或能力不匹配的具体原因及处理入口 |
| 共享 Key 只有一条通过 | 保留逐项结果，必要验证不全时不能启用或应用 |
| 检测过期 | 阻止用过期证据确认新变更；已生效服务是否继续由有效运行状态决定，不能仅因报告超过 24 小时自动停服 |
| 最后一条在用映射退出 | 先停服务，再停用路由，再解除映射；不要求空固定路由生效 |
| 渠道仍被未上架或已下架服务引用 | 删除仍受阻，显示引用并提供解除路径，不以可见性替代引用检查 |
| 供给替换失败 | 原路由继续有效；新资源保留以便修正，不能删除合法旧记录 |
| 密钥泄露、资源强制不可用 | 明确确认安全影响，立即阻止相关供给；没有替代时明示服务不可用 |
| 客户看不到或调不通 | 区分展示、上架、开放范围、订购、Key、额度及供给原因 |
| 成本/用量未知 | 不补零、不造利润，保留待核算原因 |
| 模式切换或调用标识变化 | 明确客户端配置和旧订购影响，不提供静默别名或自动迁移 |
| 账号撤权或越权访问 | 禁止相应操作及数据读取，不因帮助链接或旧页状态绕过权限 |
